## 1. The Wolverine quit-to-title crash: cause and fix
**Cause.** With Wolverine in play the game runs in his native mode (`wv_nat_on`): 26 slots of the opcode store (the cart view the lifted 68000 code runs through, 0x02600000) point at his block window at 0x00300000, one more slot (T') too, `sat_wv_tb[]` holds his table addresses and `PAGE[0x30]` maps the window. "Quit to title" restarts the game's boot (`sat_home_restart`). The boot unmaps `PAGE[0x30]`, **but nothing put the 26 opcode slots and `sat_wv_tb` back**, and native mode reverts itself only while a Wolverine player is live (`wv_nat_sync`), which the title screen is not. After the restart the opcode store still sent script reads to 0x00300000, where nothing was mapped (zeros); the 68000 code followed a garbage pointer and `f_a9cb6` / `f_a9d18` did the 16-bit read at the odd address 0x0263B1E7. A restart-state bug, not a data alignment bug.

**Evidence.** My Ymir `memdump` command dumps the opcode store (256 KB at 0x02600000) and the cart tail (128 KB at 0x027DF000) as the master sees them. Same moments, three states:
- cold boot against after one quit, build without the fix (the fix7p2 source with Wolverine on, `W4`): the opcode store differs in **81 bytes in 27 runs**: the 26 table slots plus T' (0x00162f90.. against 0x00300000..); the cart tail holds the stale `sat_wv_tb` and the native block's palette rows.
- same dumps on the fixed disc recipe (W6, final heat, run `q2M6`): **the opcode store is identical to cold boot, 0 bytes, after the first and after the second quit** (also 0 on the W5 build before the heat merge). The cart tail differs in 91 bytes (first quit) and 494 bytes (second quit): not the table words: an earlier comparison of the same states on W5 found only palette-row bytes of the native block there; I did not chase the rest (loader scratch, data the game rewrites at the next load).

**Fix** (commit `dec6df9`, `saturn/guests/wolverine/wolverine.c` and `saturn/rt/kernel.c`). `sat_guest_wolverine_reset()` (declared weak in the kernel, so builds without guests do not change): when native mode is on, restore `sat_wv_tb[]` from `wv_tb0[]`, call `wv_nat_slots(0)` (restores the 26 slots and T') and clear `wv_nat_on`. `sat_home_restart` calls it right after `ldc sr,0xf0`, before the boot runs. The state is reset on the title path; no read is masked.

## 5. The distorted crate at the end of the game: found, fixed in this disc
**Owner report:** a distorted crate in the final boss scene. **Reproduced** as Predator in the stage 24 ending scene ("Move it, bub! Get to the escape pod!" and "Quickly! This ship is crashing!"): the right third of the crate shows tile noise. `ymir_hw\runs\crP6\c9.png`, `c10.png` (crop `crate_P6.png`) on the P6 disc, `ymir_hw2\runs\crateP\k1.png` and `ymir_hw\runs\endP\e1.png` on P5, and **identically on fix7n4** (`ymir_hw2\runs\endN\c3.png`, crop `crate_N.png`): an older bug, not a regression of the placement, the data moves or the late changes. As Wolverine the same scene is intact (`ymir_hw3\runs\endW6\e1.png`, `endW\e1.png`, comparison `crate_cmp.png`). The arcade, MAME `avspu` at the same moment (stage 24 warp with the clear flags, `mame24b\snap\arc_00660.png`, script `mame_stage24.lua`): crate intact.

**Ruled out first.** Tile cache eviction: `sat_gfx_stats` read live, sprite slots used 107 to 113 of the cache, missing keys 0, refused commands 0 in sprite, layer and bank. Sprite cell size and row trim: the records decode (`tools/satgfx_pack.py` mode 2) and the key is found. A misaligned read: 0 data accesses. Scaled-sprite remnants: none on screen.

**Cause.** I dumped the cart's ROM image (0x02400000, 2 MB) with a new `memdump` region in my Ymir at the moment the crate is on screen and compared it with the ROM image plus the regions the stage 24 file loads (`R190.BIN`): 5,756 bytes differ, **4,561 of them inside spill segment 1 of the sprite tiles (ROM 0xbf000 to 0xd57d0), 355 in segment 0 and 210 in segment 4, the segments that sit on ROM pages the stage does not read.** The bytes found there are small 16-bit words (`02aa 02ed 0300 ...`), not tile data. A write trace in Ymir (every master write into 0x024bf000 to 0x02514000, by PC) gave the writer: **`sat_guest_loaded`** (`guests.c`, after every round file load: `guest_pal_sync`, `guest_dialog_sync`, `guest_name_sync`). They write the arcade's (or Wolverine's) palette tables, story box words and name fields into the ROM image "wherever the bytes differ" (`guest_pal.h`: "a guest that is off never changes a byte", which holds only while nothing else lives on those bytes). The round file planner did not know those ROM pages are written: three of the Predator stage 24 file's 24 sprite spill segments (0, 1 and 4) overlap pages the sync routines patch (palette table copies at ROM 0x100660, 0x101660 ... 0x10c660, dialogue records from 0xbf01e on), so at every file load the sync overwrote spilled sprite records with palette and text words. The crate's right side uses records in segment 1, hence the noise. The Wolverine variant of the file has another spill layout (6,867 spilled tiles in 13 segments instead of 8,397 in 24), none on those pages, which is why it was intact. The same mechanism can damage any other stage file whose spill lands on those 54 pages; stage 24 is the one the owner saw.

**Fix** (commit `eb072c8`, `saturn/rt/build.py`). `guest_sync_pages()` reads the generated palette, dialogue and name tables (`wd\gen\guest_hudpal.inc`, `guest_dialog.inc`) and every round file keeps those 54 one-kilobyte pages as the ROM has them, exactly like the story caption pages (`STORY_PAGES`): no tile spill there, and `round_keep.json` carries them for `tools/check_round_pages.py`. No runtime code changed. `GUEST_SYNC_KEEP=0` builds without (A/B). **Verified on the disc with the fix** (`P7`, the crate fix alone; the final disc P9 below): the same ROM image diff at the crate moment: 3,059 bytes differ from ROM plus file (the game's own writes), **none inside any of the 53 spill segments** (before: 5,126 in three of 24). Crate whole in `ymir_hw3\runs\crP7\c2.png` (crop `crate_P7.png`). Cost, from the build logs: keeping the 54 pages splits the free runs, so the stage 24 file now has 53 spill segments instead of 24 (spill counts move by one tile in 81 files); the ISO grows from 315.9 MB to 330.6 MB (more ROM restore regions in every file); **the Boss Rush file (stage 0e and its 10 variants) drops 659 lowest-ranked sprite keys where it dropped 323** (the file was already over its room; the dropped keys are the least used frames) and no other file drops a key. I looked at the five Boss Rush fights for missing sprites (`ymir_hw2\runs\rushS`) and saw none, but I did not compare the frames one by one. **On the final disc P9** the same dump: 53 spill segments, 3,059 differing bytes, **0 inside the spill segments**, and the crate is whole in the dialogue scene ("Go on!! I'll catch you in a minute!"): `ymir_hw3\runs\crP9\c1.png`, `c2.png` (sheet `crate_P9.png`). Wolverine's ending run `endW9` (`ymir_hw3\runs\endW9\e1..e24.png`, sheet `endW9_sheet.png`) reaches the same scene with its crate whole and runs through credits, ranking and title, 0 data accesses. No earlier disc carried coalescing and all of them showed the crate bug (fix7n4, fix7p1, fix7p2, P5, P6), so the coalescing corruption, which the loading lane found and fixed, is not the cause; the cause is the guest sync above.


## 6. Faster loading (owner approved, from lane loading): `SAT_LOAD_COALESCE` and `SAT_BOOT_DISC_ORDER` ON
Taken from `lane/loading-20261112` (the fixed version, commit `18921a6b`): `saturn/rt/boot.c` (loader, `BOOT_CFLAGS`), the two reviewed cast sites in `tools/align_sites.txt` (48 reviewed sites now), `tools/loading/coalesce_replay.py` and `expsum.py`. **Left out: `SAT_TR_LINE`** (costs a cart step; it stays in its branch). The test-only `SAT_LOAD_SUM` is built only into the two test discs below, **never in the shipped recipe**. Recipe of the shipped disc: the five fix7p2 switches in `KERNEL_CFLAGS` plus `BOOT_CFLAGS=-DSAT_LOAD_COALESCE -DSAT_BOOT_DISC_ORDER` (build log head of `P9`: `tag P9`; `BC` in `pbuild2.sh`).
- `SAT_LOAD_COALESCE`: the dozens of tiny ROM-restore regions a round file lists (about 35 per stage file, about 70 in the front end file) were each their own GFS read, hence their own CD play command; groups of them are now read in one go into the pack room and copied to their addresses. The first version staged regions over the tile region after it had been read and **corrupted the tile region of 157 of the 287 round files**; the fixed version (`coal_big`) stages nothing once the tile region is in.
- `SAT_BOOT_DISC_ORDER`: the five boot files are read in the order they lie on the disc (COLD1, HW, LW, OPX, ROM), so the drive sweeps forward once. Ymir cannot price seeks (flat 33 ms), so it shows no change there; the gain is for the console's drive.
