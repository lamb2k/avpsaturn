# fix7n (native crop), the record latch and the review follow-ups (2026-11-11)

Builds on `AVP_HWBOOT_FIX7_20261111.md`. Discs: `avp_3h_A_fix7` (as staged, kept), `avp_3h_A_fix7b` (fix7 + the record latch, scaled), `avp_3h_A_fix7n` (native crop, FIT 2, + the record latch). fix6d stays shelved.

## 1. Latch coherence: the review was right, fixed
Verified in `sat_gfx.c` (fix7 as staged): `VDP2L` wrote `lat_val[reg]` at the moment the draw reached that line (priorities early, scroll registers last), and `lat_apply()` at V-blank IN copied whatever the table held, so a vblank could apply the early registers of picture N+1 with the late ones of picture N; 0xFFFF meant "not set" (no register used it, but nothing forbade it); and it ran before the frame-change decision, so the VDP2 state could run ahead of the VDP1 picture. Fix: the draw stages every write in `lat_wr` with a separate valid flag `lat_wv`, `lat_publish()` copies the whole staged state into `lat_pub`/`lat_pv` at the end of the draw under a sequence word (odd while copying), and `lat_apply()` writes the last complete record, re-reading if the sequence changed (4 tries, counters `sat_lat_retries`, `sat_lat_skips`). The VDP1/VDP2 alignment is unchanged from before the latch (not bound to the frame change: the plot serial is not available in every mode). Evidence: strict Ymir trace, fix7n build: 12,168 vblank entries, 11,569 apply bursts of exactly 24 registers (the cfg's valid set) and no 48-register (retried) burst, 0 direct display-register writes by the slave; one HUD in every frame of 40 consecutive stage-1 shots (fix7b, fix7n). Not proven: a torn read is impossible by construction (seqlock), but Ymir does not interleave the two CPUs at that grain, so a real retry has not been observed.

## 3. CPU slot rule
Source text read: Sega ST-58-R2 (the 06/01/94 manual, https://antime.kapsi.fi/sega/files/ST-058-R2-060194.pdf, pp. 35-36) says, for divided VRAM, the CPU command goes in both banks at the timing and "in the registers of both bank 0 and bank 1 of the timing before the set CPU read/write access command timing, the access command that won't access must be selected", with an exception for linked CPU timings (only the timing before the first). The SOA-6 bulletin of 1995-08-16 is NOT in that file (searched for SOA, bulletin, 04EEEE, 5FEEEE: nothing), so the claim that later guidance drops the no-access rule could not be checked; if it is right, the examples A0 `04EEEEEE` / A1 `5FEEEEEE` (CPU from T2 with a cell read right in front) show it is stricter than the hardware. fix7's CPU slots are right either way: A0/A1 have CPU together at T7 with no access at T6 in both banks, B0/B1 together at T4-T7 with no access at T3; under the loose reading they are simply valid pairs. The checker keeps the strict reading (a possible false alarm is cheap, a missed real rule is not); its positive control is the retail MSHvSF set.

## 4. MSHvSF's words against the checker
From `CPS2_PORTS_FIT_20261111.md` (steady play state): A0/A1/B0 `6745 FFFE` (cells of NBG2 T0, NBG3 T1, NBG0 T2, NBG1 T3; CPU T7 after no access T4-T6), B1 `CD01 23FE` (vertical cell scroll NBG0 T0, NBG1 T1, names NBG0 T2, NBG1 T3, NBG2 T4, NBG3 T5, no access T6, CPU T7). Checker (test added): with MSHvSF's own layout (all maps in B1, cells in A0/A1/B0) it passes all rules, CPU slots A: T7, B: T7. With our layout (maps in A0/A1, NBG1 cells also in B1) it fails (names would have to be in B1). So: the rules are not too strict for a retail game; its CPU gets T7 only (the T5-T7 in the research note belongs to another profile). Native words shipped: ours, `231F 67FE / 0F4F FFFE / 5FFF EEEE`: same legal-cell and pair rules, names in A0/A1 as our map layout needs, CPU A: T7 and B: T4-T7, so at least MSHvSF's CPU time. Moving every map to B1 would copy Capcom more closely but is a VRAM re-layout (NBG1's 256 KB of cells cannot sit in B0 alone), not done.

## 5. fix7n: what changed and what was checked
- **FIT 2 ships, not FIT 0.** FIT 0 is the plain centre crop: the HUD loses its left 16 pixels (1P tag, portrait) and the right end of the 2P line, which breaks "keep all HUD info"; FIT 2 keeps the HUD rows flush (middle 4 columns dropped, nothing lost at the edges).
- **Loader/game mismatch closed.** `build.py` `boot_flags()` adds the kernel's `-DSAT_GFX_FIT` to the loader's flags and stops (NO-GO) if BOOT_CFLAGS names a different value. The default build has no boot-display restore at all (the kernel's graphics init sets every register and ends the display), so the mismatch could only bite SAT_BOOT_DIAG builds; the trace of the fix7n build shows only the native words (`231f 67fe 0f4f fffe 5fff eeee 5fff eeee`, ZMCTL 0) in every judged state, 0 rule breaks in 11,569 bursts; fix7's trace (earlier) shows only the fit-1 words; fix7b was played in Ymir but its register trace was not run separately (same cfg, same loader flags).
- **Text placement.** `home_row_map` (sat_gfx.c) for SAT_GFX_FIT == 2: the character select's fixed tables and the dynamic 4-drop map were calibrated to 11/12-scaled art and moved text 8 to 24 px against unscaled art; now a plain 16 px crop (source columns 2 to 45) on every row, except a block of rows with something in the outer 2 columns on a side that is not a HUD row, which keeps the squeeze (4 blank columns dropped) so full-width lines stay whole. FIT 1 is untouched.
- **Checked in strict Ymir (screenshots in the lane evidence folder, scratchpad `n2_*`, `sheet_n2.png`, `rank_n2.png`):** title, menu, character select (labels, bars, plates, timer, "START:PLAYER=1 CONTINUE:PLAYER=2" aligned and complete, outer silver frames cut), stage 1 as Schaefer (health bar, portrait, name, score, 1P/2P "PRESS START" complete, text aligned through the loading/entry transition and gameplay), continue screen (48-column line whole), ranking (RANK, POINTS, NAME, portrait, ROUND all visible). **Not checked:** boss HUD, stage select list, option screens, game over, round title, story captions, the CREDITS line, a Wolverine pick, the reveal, and how often enemies, projectiles or attacks use the outer 16 px (needs play, not stills).
- Speed readout: `DONE 60` in Ymir (not meaningful there).

## 6. Confidence and go / no-go
**Go for fix7n as the first console disc; fix7b second; fix7 (as staged) only as a reference.** Estimates, mine, not measurements:
- *fix7n*: about 60 % that the vertical stripes are gone. It removes the half-reduction and the scaled sprites and meets every manual rule (1 name + 1 cell per layer, legal slots, a valid CPU pair), in the same class as the retail Marvel disc, and the schedule gate and trace pass. It does not rule out the NBG2 question in section 2, and a clean fix7n would show reduction was *a* cause, not the only one. About 90 % that it is not worse than fix6 (new text placement, moved NBG0 map, record latch are emulator-verified only).
- *fix7b* (scaled, record latch): about 35 %; it depends on the 2-name schedule being right and on NBG2 not being a separate problem.
- *fix7 as staged*: about 30 %, the same as fix7b minus the latch repair.
Hardware-only: whether any of the stripes go, the picture rate, the CPU slot throughput, the new text placement on boss HUD / options / stage select, edge gameplay.
