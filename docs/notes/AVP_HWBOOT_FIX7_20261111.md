# fix7: the game disc with the VDP2 memory schedule rebuilt from the manual (2026-11-11)

Branch `lane/hwboot-20261110`. Owner decision: no more manual diagnosis on the Saturn; one game disc, tested only when confidence is high. fix6d stays in the tree and on disk, shelved.

## What was changed (all of it checked off-hardware first)
1. **One source of truth.** `saturn/gfx/sat_vdp2_cfg.h` holds the VRAM layout, RAMCTL, CHCTL, PNC, PLSZ, MP*, ZMCTL and the eight cycle words for fit 1 (half reduction) and fit 0; sat_gfx.c, sat_gfx.h, boot.c (the loader's restore after the boot display) and fps_hud.c use its macros. SAT_GFX_FIT 3 (run-time zoom switch) is an #error now.
2. **Schedule from Sega's VDP2 manual, chapter 3** (mirror https://www.infochunk.com/saturn/segahtml_en/hard/vdp2/hon/p03_31.htm, p03_33, p03_34): Table 3.2 names per cycle 1 / 2 / 4 for 1x / 1/2 / 1/4 reduction; Table 3.3 cell reads (16 colours 1 / 2 / 4); Table 3.4 legal cell timings per name timing; split banks: CPU in both banks at the same timing with no access in front in both; names in at most one of A0/B0 and one of A1/B1. fit 1 words (low = T0..T3, high = T4..T7; 0..3 names NBG0..3, 4..7 cells, E CPU, F none): A0 `2311 67fe` (NBG2 names T0, NBG3 names T1, NBG1 names T2 T3, NBG2 cells T4, NBG3 cells T5, CPU T7), A1 `004f f4fe` (NBG0 names T0 T1, NBG0 cells T2 T5, CPU T7), B0 and B1 `55ff eeee` (NBG1 cells T0 T1, CPU T4..T7). fit 0 words: `231f 67fe / 0f4f fffe / 5fff eeee`. RAMCTL stays 0x1300.
3. **CPU / transfer policy: live-transfer allocation, implemented.** The legal packing of the old layout filled A0 completely (6 names + 2 cells) and left VRAM-A no CPU time. Holding every VRAM-A write to the blanking would mean restructuring the slave's per-picture tile and name writes (hundreds per picture); rejected. Instead NBG0's map moved to bank A1 (one 16 KB 2x2-page plane at 0x3C000, MPAB0 = MPCD0 = 0x3C3C), which frees one slot pair: CPU gets A: T7 (A0+A1 together, T6 no access), B: T4..T7 (B0+B1, T3 no access), plus blanking. Cost: scroll 2 cache 895 tiles (was 1024), scroll 3 510 (was 512); hw_free rose from 1,640 to 2,608 bytes (the slot tables shrank). Not measured on a console: whether the write speed is enough.
4. **Blank tiles in their own bank.** Empty scroll 2/3 tiles used a name pointing at the scroll 1 slab in A0, a bank NBG0/NBG1 have no cell read in. Each layer now has its blank character in its own bank (NBG0 0x3BF80 in A1, NBG1 0x7FC00 in B1); the checker flags a cell location without a cell read.
5. **GAME relabelled.** `DONE n` = game frames completed per second = vblanks minus MISS, normalised to 60. `FLIP n VBL n` is the old raw object-bank-select count and the window's vblanks (third line). The old GAME stayed 60 while MISS was 38 to 39 of 60: a vblank restarts the dispatcher's task walk and an early task flips the bank each time, so it counted starts, not completions. Console readings fix5: PIC 25 / MISS 39 and PIC 23 / MISS 38 mean about 21 and 22 completed frames per second.

## Cross-checks
- Ymir's `CalcAccessPatterns` comments list schedules of shipped games that ran on real consoles, with what Ymir's author saw. Run through the checker: Cyberbots in-game (four NBGs) breaks no rule; X-Men vs. Street Fighter (cases 20, 21) breaks Table 3.4 (cell at T4 with names at T2, cell at T5 with names at T3) and Ymir records "delay" (graphics one cell to the right) for case 21; World Heroes Perfect (case 15) breaks it (cell at T3 with names at T0) and shows "skip" (one cell left). So Table 3.4 violations do change what a real console draws. Table 3.4 equals Ymir's masks, which come from those games.
- SGL / Brooklyn Bangout register logs (`regs_sgl352.log`, `regs_brooklyn.log`, programs that run on the owner's console): their running states pass the split-bank CPU pair rule (A0/A1 `FFFE EEEE`, B0/B1 `FFFF EEEE`, no access in front of the CPU run). SGL's first default state (3 bursts, before its layer set-up) has CPU time in B0 but not B1 and breaks the pair rule; the name and cell rules cannot be applied to those logs (NBG1 has no names scheduled there, the layers are not configured yet). So the manual's pair rule is followed by the hardware-proven programs, but it is not the whole story.
- No commercial disc is on this PC; nothing was copied.

## Strict Ymir enforcement: not done as a model, and why
Ymir cannot tell us what the VDP2 draws when a count is short: its `CalcAccessPatterns` ignores the name count and the reduction multipliers are commented out because they broke a shipped game. Making patched Ymir blank columns or tiles when counts are short would encode a guess about the hardware and then "reproduce" the stripes from that guess, which proves nothing. What is feasible and done: the same rules judged on the exact register state of a real strict-Ymir run (`vdp2_trace_check.py`), as a regression test for the schedule. The stripes themselves stay unreproducible off the console.

## Confidence
Supported off-hardware: (a) the schedule follows the manual rule by rule and passes an automated check that fix5 and fix6 fail; (b) the rules it checks are the ones whose violations real consoles are known to turn into visible shifts (X-Men, World Heroes) and the ones the hardware-proven programs follow (the CPU pair); (c) the two layers that broke two rules (NBG0, NBG1) are the two that striped on the console, and the two that broke none (NBG2, NBG3) were clean; (d) the new memory layout runs the game in strict Ymir, with a single HUD.
Only the Saturn can show: whether the stripes are gone (the cause is inferred, not proved: the manual says what the VDP2 needs, nothing says what a short name count looks like), the picture rate, whether the CPU slots are enough for the tile writes, and that nothing else in the new layout (moved map, 510 / 895 tile caches, blank characters) misbehaves on the real chip.
